## 启动：不需要 Node、MySQL、Redis 或 Docker

需要 Python 3.10 或更高版本；当前验收环境为 Linux / Python 3.13。

```bash
cd jingman-lab
bash run.sh
```

首次运行若当前 Python 未安装本次验收锁定版本的运行依赖，脚本会创建项目内 `.venv`，从当前配置的 Python 软件源安装 `requirements.txt`。这一步需要联网；安装后，整个业务演练无需外网。

终端会显示带本机实验室访问口令的地址。打开该地址即可进入；后续可以在网页右上角切换顾客、店长、拣货员、配送员、另一位顾客和第二门店店长。**身份切换只用于持有本地实验室口令的演练，不是正式商城的登录设计。**

默认仅监听 `127.0.0.1:8765`，没有公网监听参数。不要通过代理把这个实验室暴露给不可信访问者。项目也没有真正收款的生产模式。

不使用 Bash 时：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m backend
```

更换端口、指定独立数据库，或者暂停自动任务：

```bash
bash run.sh --port 8899 --data-dir ./my-lab-data --no-worker
```

`--no-worker` 适合手动测试打印/退款故障。默认模式每 3 秒处理待执行与失败任务，并检查未付款订单是否过期。所有真实用户状态存储在数据库，而非 JavaScript 静态数组。

## 一条能实际操作的演练路线

进入顾客端，把 **2份进口香蕉 + 1箱蒙牛纯牛奶**加入购物车。商品金额为 ¥30.74。结算时选择门店配送与“满30减3”优惠券：抵扣 ¥3.00 后未满免运费门槛，因此收取 ¥3.00 配送费，应付仍为 ¥30.74。预置地址是配送范围内的虚构样例。

提交后订单为待付款，库存先被预占。点“模拟微信付款”，可以分别测试“模拟失败”和“确认模拟付款”。失败不改变付款状态；成功写入本地模拟网关账本，再处理签名回调和库存扣减。

切换到店长，在实验室开启“打印机离线”和“退款网关超时”。执行“重试待处理任务”，能看到打印失败，但订单付款不会被撤销。

切换拣货员，打开订单，接单，给香蕉登记缺1件，然后拣齐剩余商品并完成打包。系统按优惠分摊后金额退差价；在本样例中缺1份香蕉退款 **¥3.59**，不是未经折扣的 ¥3.98。

回店长实验室驱动退款任务，观察失败状态；恢复两个开关，再重试。订单不会重复退款，小票不会重复生成。店长呼叫模拟骑手，然后在配送员身份下依次接单、确认取货、确认送达。最后用顾客身份申请售后，由店长审核、队列执行退款并对账。

另一个独立场景是自提：顾客下单后，店员拣齐打包，顾客订单中出现6位自提码，店员输入正确码核销。没有完成打包或输错码不能提前完成订单。

## 微信小程序源码

用微信开发者工具导入本包的 `miniprogram/`。这是原生 **WXML / WXSS / JavaScript** 项目，不需要 npm 构建依赖；配置中使用 `touristappid` 作为本地占位，需要有效 AppID 的工具环境应填自己的测试 AppID。

先在同一台电脑上启动后端，再在小程序连接页填写本机地址和终端显示的访问口令。`project.config.json` 中的 `urlCheck:false` **仅用于开发者工具的本机 HTTP 联调**。这不是正式发布配置。

15 页包括连接、首页、分类、商品、购物车、结算、订单列表、订单详情、个人中心、地址、优惠券、工作台、库存、故障实验室和骑手任务。完整商品新增、改价、分类/发券、门店设置和导出界面在网页工作台中，使用同一后端。

**本次执行了 15 页路由/文件/WXML绑定检查，以及 Page 控制器经真实 HTTP 操作数据库的契约测试。没有把 Node 中的控制器执行冒充微信开发者工具编译、WXML渲染或手机真机验收。**正式微信身份、微信支付 API v3、订阅消息、真实骑手/打印机/POS 厂商仍需分别接入与实测。

手机上的 `127.0.0.1` 是手机自己，不是你的电脑；此交付的微信端联调范围是电脑上的开发者工具。详见 `docs/WECHAT.md`。

## 数据库和接口

初始数据：2家演练门店、6个演练身份、16个SKU、6个分类、2个虚构地址、6张优惠券和开户库存流水。没有预置伪造的历史销量；工作台统计来自真正创建的订单。

默认数据位置：

```text
$XDG_STATE_HOME/jingman-lab/
# 未定义 XDG_STATE_HOME 时：~/.local/state/jingman-lab/
├── credentials.json   # 每次新安装随机生成，权限0600
└── jingman.sqlite3     # 实际持久化的订单、库存、账本
```

建表脚本在 `backend/schema.sql`，种子数据在 `backend/db.py`。原始工作区的 `sample-data/initial.sqlite3` 是没有登录会话和订单的示例数据库；新的商家开发交付 ZIP 不携带数据库，运行器首次启动会自动创建独立演练库。

备份已有数据库（可在服务运行时执行，不覆盖已有备份）：

```bash
python3 tools/backup.py \
  --source ~/.local/state/jingman-lab/jingman.sqlite3 \
  --destination ./backups/jingman-001.sqlite3
```

自定义了 `XDG_STATE_HOME` 或 `--data-dir` 时，按实际位置调整源路径。备份文件权限为0600；备份数据库不包含另一个文件里的实验室登录口令。恢复时应先停止服务，保留旧库副本，再替换数据库。

服务启动后访问 `/docs` 查看**不依赖外部 CDN**的接口文档，或访问 `/openapi.json`。仓库还包含固定生成的 `docs/openapi.json`。

## 重跑验收

运行应用只需 Python 依赖；完整测试另外需要 Node.js 和 Chromium/Chrome。

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-test.txt
# 没有本地 Chromium/Chrome 时，安装 Playwright 的测试浏览器：
.venv/bin/python -m playwright install chromium
bash verify.sh
```

完整测试为 API / 数据库单测、原生控制器契约、真实 localhost HTTP 并发和浏览器 UI 流程。它使用 `tempfile` 创建独立数据库，不清空你的实际演练数据；启动的测试子进程在结束后关闭。

```bash
bash verify.sh --core       # API + 原生控制器 + HTTP并发，不声称执行浏览器验证
bash verify.sh --http-only  # 只重复真实HTTP并发实验
```

本次环境的 Chromium 管理策略禁止顶层 URL 导航，因此网页验收采用 `--renderer`：加载同一份页面 HTML/CSS/JS，使用隔离的会话存储，并将 `/api/` 请求通过测试桥转发到真实监听中的后端。没有预置 API 返回值。**它验证 DOM交互/页面状态/真实API联动，不覆盖浏览器原生导航、同源、CSP执行或微信渲染器。**普通本地环境默认不加该参数，直接打开真实 localhost 页面。

```bash
bash verify.sh --renderer   # 仅限明确需要上述渲染模式的测试环境
```

历史结果文件在 `evidence/`，新验收写入独立的 `output/verification/日期时间/`；默认不随发行包分发可能包含临时会话凭据的原始浏览器 trace，重跑浏览器测试时会在本机生成。范围、每个通过项和迭代记录见 `docs/ACCEPTANCE.md`。曾经失败的首轮记录也保留，不能误读为最终未修复的问题。

## 实现边界

本系统把核心购物、订单履约、缺货/售后退款、库存、权限和故障恢复做成了可以验证的本地业务。它没有实现正式收款、消费者实名登录、外部渠道推送、实物配送/打印、采购供应链、称重补差价、批次保质期、多商户清分或任意数据库一键切换。已有库存/财务一致性检查，也不能替代独立安全审计。

未经独立真实集成与生产审查，不能把实验室模式直接用于真实经营。项目不内置商户密钥、没有从受限SQL附件复制业务库，也没有把模拟成功包装成实际第三方接入成功。
