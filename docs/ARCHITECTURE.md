# 实现结构与数据不变量

## 运行结构

网页顾客端、网页门店工作台和原生小程序 `wx.request` 访问同一套 FastAPI 接口。`backend/service.py` 是事务型零售服务，`backend/db.py` 提供 SQLite 连接与事务，`backend/schema.sql` 定义表、约束与只追加流水。CLI 将环境限制为本机实验室。

小程序不持有数据库连接或签名密钥。客户端提交 SKU、数量、地址和优惠券选择；后端自行计算成交价格。示例采用固定规格商品，没有用“约500g”悄悄实施实际称重收费。

## 金额、库存与状态

金额存整数分。优惠使用最大余数法分配到订单行；逐件缺货退款按累计比例差计算，最后一件能补齐分摊尾差。订单使用商品、价格和地址快照，历史订单不会被改价或地址删除改写。

可售库存 = 账面库存 − 未付款订单预占。下单用事务预占；付款确认用事务同时减少账面和预占；取消或超时释放未付款预占。每个变化同时写库存流水。缺货退款不会把不存在的实物补回库存；已交付订单售后退款也不会自动当作商品已退回。

数据库 `BEGIN IMMEDIATE` 序列化写入，库存更新带非负和预占约束。它适合本次本机演练，不是大型分布式并发架构或容量承诺。

主要订单状态：pending_payment → paid → picking → ready → delivering → completed；自提在 ready 验码后直接 completed。取消、超时、退款处理中和退款完成有独立分支。所有迁移按角色、门店和前置状态校验。

## 不把外部副作用塞进库存事务

支付演练分为模拟网关扣账与回调处理两步，用不同数据库事务模拟真实外部边界。回调验证 HMAC、时间窗口、金额、币种、订单和网关交易号。此协议明确是实验室协议，不是微信支付 API v3。迟到付款不能复活已释放库存的订单，而是进入退款流程。

小票、通知和退款由 outbox 处理。消息状态包含 pending、failed、done；失败保留原因和尝试次数，恢复后重试。退款有独立业务记录及网关账本唯一引用。小票用订单唯一引用，重复执行不会重复出单。

## 权限

演练角色切换必须先持有随机实验室口令，后端才发放签名无关的随机 Bearer 会话；会话在数据库只保存哈希。顾客订单按本人限制，员工操作按门店和角色限制，骑手使用脱敏任务接口而不能访问完整订单接口。二号店店长不能操作一号店库存、订单和管理工具。

接口并不依赖前端隐藏按钮实现权限。关键记录通过审计日志和库存流水留痕；只追加约束是数据库级业务保护，不宣称可以抵御拥有数据库最高权限者的恶意篡改。

## 对账

一致性检查核对库存快照与流水累计值、预占与未付款订单数量、订单行金额、已付/已退金额与模拟支付账本。未确认的付款回调单独列出。故意改坏库存快照的测试必须被对账发现。

## 未来真实集成位置

支付：替换模拟网关及回调认证协议，保留金额、订单一致性、幂等与对账规则。微信登录：替换实验室口令/角色切换为真实用户身份校验。配送：用适配器提供询价、下单、取消、查询及签名回调。打印：将 outbox 作业连接实际厂商并核对设备状态。POS：建立厂商商品条码映射、幂等销售事件、补货事件和断网补偿。

这些是清楚的接线边界，不是已经完成的第三方接入。改用其他关系数据库时，还需要迁移SQL方言、事务语义、约束、备份方式，并重复并发实验。
